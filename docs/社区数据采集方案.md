# 社区数据采集方案

> **为什么有这个文件**：原计划的"访谈 2–3 位转专业同学"执行受阻——没有可接触的转专业学生。
> 本方案是**替代路径**，目标是用**公开社区数据**建立同样有力、且**更可复现**的证据链。
>
> 拟定的采集日期：2026-10-16　预计耗时：**半天**

---

## 为什么社区数据反而更好

不是退而求其次。对比一下：

| | 访谈 | 社区数据 |
|---|---|---|
| 可复现 | ❌ 评委无法重做你的访谈 | ✅ **同样的关键词能搜到同样的帖子** |
| 样本量 | 2–3 人 | 30–50 条 |
| 是否被引导 | ⚠️ 受访者的回答受提问方式影响 | ✅ 发帖发生在我们在场之前 |
| 可量化 | ❌ 只能定性描述 | ✅ 帖数、浏览量、矛盾数都是数字 |
| 需要社交资本 | ✅ 需要（本项目正卡在这里） | ❌ 完全不需要 |
| 幸存者偏差 | ⚠️ 严重（转成功的人才愿意讲） | ✅ **被刷的人也会发帖求助** |

最后一行是关键。访谈只能抓到愿意跟你聊的人，而社区里**"我转专业被刷了怎么办"这类帖子恰恰是被淘汰者写的**——那才是我们最需要的样本。

> 这一点不是自夸，是评分表 25% 那一项「**评委可一键复现**」直接对应的：我们的证据链越可复现，那一项分越高。

## 一、采集范围

### 平台（按优先级）

1. **学校贴吧** —— 本校吧 + 2~3 所有转专业热度的学校吧（"转专业"是每学期固定话题）
2. **知乎** —— 「转专业」话题下的问题与回答
3. **小红书** —— 转专业经验贴（评论区常比正文有料）
4. **B站 / 微博** —— 转专业视频与超话的评论区

### 关键词（**必须记录，评委要靠它复现**）

在此列出**实际使用过的完整关键词清单**，这是可复现性的凭证：

```
转专业 难吗         转专业 条件          转专业 要求
转专业 流程         转专业 绩点          转专业 成绩 排名
转专业 笔试         转专业 面试          转专业 考什么
转专业 学分 折抵     转专业 学分 认定      转专业 补修
转专业 后悔         转专业 延毕          转专业 被刷
转专业 时间 什么时候
```

### 目标样本量

**30 条以上**"提问 + 回答"的完整对话。低于 20 条说服力不足。

## 二、记录字段（编码表）

每条帖子一行，存为 `docs/调研原始材料/社区帖采集表.csv`：

| 字段 | 说明 | 示例 |
|---|---|---|
| `编号` | 顺序号 | 07 |
| `平台` | 来源 | 贴吧 |
| `采集日期` | | 2026-10-16 |
| `发帖日期` | 帖子原始日期 | 2025-11-03 |
| `提问原话` | **逐字照抄，不要改写** | 转专业难吗，通识课分数真的要卡到70分吗 |
| `浏览量` | 有则记 | 822 |
| `回答数` | 收到的回复条数 | 5 |
| `涉及维度` | 见下方枚举，可多选 | 门槛;时间 |
| `回答要点` | 一句话概括 | 不能挂科；考核高中+专业相关知识 |
| `是否互相矛盾` | 是 / 否 | 是 |
| `矛盾点` | 矛盾在哪 | 一说"包转"，一说"要笔试面试筛选" |
| `是否引用官方出处` | **是 / 否** ← 关键字段 | 否 |
| `截图文件名` | | 社区帖/07_贴吧_门槛.jpg |

### 维度枚举（编码用，不要临时造新词）

```
门槛      —— 挂科 / 绩点 / 成绩排名 / 分数要求
时间      —— 什么时候考 / 什么时候申请 / 窗口期
流程      —— 找谁办 / 填什么表 / 多久走完
考试      —— 笔试考什么 / 面试问什么
限制      —— 专业限制 / 校区限制 / 艺术类等特殊类别
学分折抵  —— 已修课如何折算
补修      —— 需要补哪些课
情绪      —— 后悔 / 迷茫 / 焦虑 / 纠结
```

## 三、产出（三条统计，直接进技术文档）

采完之后，算三个数：

### 1. 维度频次 → 真实痛点排序

统计各维度被提及的次数，降序排列。**这个排序直接决定 MVP 各模块的优先级**，而且是有数据支撑的，不是拍脑袋。

### 2. 矛盾率 → "信息不可信"的量化

> 例：**42 条回答中，有 17 条对同一问题给出了互相矛盾的说法。**

一个数字说明"靠口语经验获取信息不可靠"。

### 3. 官方出处提及率 → **产品存在的理由**

> 例：**42 条回答中，只有 3 条引用了官方文件或指明出处，93% 依赖回答者个人经验。**

**这是最有杀伤力的一个数。** 它把"官网有详细介绍"（原话）和"学生还是到处问"之间的矛盾，压缩成一个可引用的百分比。技术文档的痛点论证，用这一条就够了。

- [ ] 把统计结果写回 `docs/用户调研.md`
- [ ] **记录实际使用的关键词清单**（可复现性凭证）

## 五、匿名化要求（**截图不入库**）

本项目是**公开仓库**，而社区帖截图里必然包含第三方用户的昵称与头像。
为保护与本研究无关的第三方，规则如下：

- **截图一律不提交到 Git。** 存本地目录（如 `docs/调研原始材料/社区帖/`），
  该路径已被 `.gitignore` 排除；仓库里只保留 `社区帖采集表.csv` 与逐字摘录
- 编码表中**不记录任何用户名、校名、真实姓名**
- 文档里引用原话时只写"某校园社区用户，2025-11"，不写昵称
- 若某条原话必须保留截图才能理解（如图表/排版），**改为把文字抄录下来**，而不是贴图

> 为什么这么定：这三张早期截图曾随仓库提交并推送到公开仓库，后来做了历史重写才清除。
> 事后清理的成本远高于一开始就不提交——所以把这条写成硬规则。

## 六、时间预算

| 阶段 | 时长 |
|---|---|
| 搜索 + 截图 | 2 小时 |
| 填编码表 | 1.5 小时 |
| 统计三条数字 | 0.5 小时 |
| **合计** | **半天** |

如果时间紧张，**优先保证 30 条已采集数据的质量，不要为了凑数降低标准**。20 条扎实的比 50 条潦草的强。
